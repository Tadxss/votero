# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Votero — a QR-code-based group voting/polling app, shipping to iOS, Android, and Web from a single Turborepo monorepo with shared business logic. See [TECH_STACK.md](TECH_STACK.md) for the mandated stack and [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) for the concrete product design (Postgres schema, RLS policy design, Edge Functions, Realtime channel design, build order, and what's deliberately deferred).

**Status**: backend is built and verified end-to-end (schema, RLS, RPCs, all 4 Edge Functions), both against a local Supabase stack and the real hosted project, deployed live on Vercel. The web creator/voter UI (`apps/web/app/{create,lobby/[code]/manage,vote/[code]}`) plus optional creator accounts + lobby history (`/login`, `/lobbies`, email-OTP sign-in) and profile editing (username + first/last name via a header-triggered modal, `rpc_update_profile`) are built and verified via scripted Playwright browser runs — see `docs/TESTING.md` for the manual walkthrough version. Creator-facing pages (`/create`, `/lobbies`, `/lobby/[code]/manage`) use a responsive wide-dashboard layout on `lg:` and up (two-column forms, a real table on `/lobbies`) while staying single-column on mobile; the voter-facing `/vote/[code]` and `/login` stay centered cards at every size. Signed-in creators are capped at 10 lobbies (enforced in `rpc_create_lobby`, exempting anonymous creators); anonymous-created lobbies self-delete 7 days after creation via a `pg_cron` job; creators can also manually delete any of their own lobbies at any time (trash icon on `/lobbies`, "Delete lobby" on the manage page, both behind a shared `ConfirmDialog`). `/lobbies` also has a table/grid view toggle (desktop only, persisted in `localStorage`). The manage page's QR card has Copy link/Copy code/Share (`navigator.share` with a clipboard fallback) actions. The home page has an equally-weighted "Join a lobby" button next to "Create a lobby," opening `JoinLobbyModal` (`apps/web/app/_components/JoinLobbyModal.tsx`) — a real in-browser camera QR scanner (`getUserMedia` + `jsqr`, chosen over the native `BarcodeDetector` API for Safari support) with a code-entry fallback. Anonymous creators see a small notice on the manage page stating exactly when their lobby will auto-delete (7 days from creation); signed-in creators never see it. Voting in an **open**-ballot lobby now requires a signed-in (non-anonymous) account — enforced in `rpc_join_lobby` — since open mode reveals identity to the creator and a free-text display name was never trustworthy; `/vote/[code]` shows a sign-in gate for anonymous visitors, `/login?redirect=...` sends them back to the same ballot after signing in. The "who voted for what" list (`rpc_get_ballot_detail`) shows real name/`@username`/email (priority-ordered) instead of the old always-null display name, with a profile photo (`profiles.avatar_url`, an `avatars` Storage bucket, `Avatar` component) alongside — uploadable from `ProfileModal`. Anonymous-mode lobbies are completely unaffected by any of this. Creators can optionally set a scheduled auto-close time on `/create` (`lobbies.closes_at`); a `pg_cron` job sweeps every minute and flips any lobby past that time from `open` to `closed`, same convention the existing cap-triggered auto-close already uses — the manage page shows "Auto-closes `<date>`" while it's pending (the voter's `/vote/[code]` shows the same date too). `/lobby/[code]/present` is a fullscreen Present Mode meant to be projected at a live event — big QR + live tally, no site header (`Header` hides itself on that route), never shows individual voter identity regardless of ballot mode, zero schema changes. Building it surfaced a real RLS bug: draft lobbies were never actually readable by non-creators despite the voter UI/docs assuming otherwise — fixed so a stranger can see a draft lobby's "not open yet" state (needed for Present Mode's pre-open screen). A lobby can now ask **1+ questions** (multi-question surveys) instead of exactly one — the biggest schema change so far (new `questions` table, `options`/`votes` gain `question_id`, the old one-vote-per-lobby DB constraint relaxed to one-vote-per-question), fully backward compatible (every pre-existing lobby got a single default question via a data migration, verified). `/create` has a repeating Questions section (own title + options per question); `/vote/[code]` is a one-question-at-a-time stepper ("Question X of Y", confirmed UX over one long scrollable page); the manage page and Present Mode both render one results block per question. A classic single-question lobby still looks and behaves exactly as before (no stepper indicator, button still reads "Vote"). The manage page's results card has "CSV" and "Image" download buttons (`apps/web/app/_components/downloadResults.ts`) — closes a real gap since anonymous lobbies auto-delete after 7 days and previously had no way to keep a permanent record; both are generated entirely client-side (no new dependency, no backend involvement), with the image hand-drawn onto a `<canvas>` mirroring `TallyBars`' visual design. A question can now be **`'choice'`** (today's behavior) or **`'text'`** — voters type a short answer instead of picking an option, additive on top of multi-question surveys (a survey's questions can freely mix both types). Text responses are grouped by frequency (`lower(trim(...))` match) and shown as small, uniformly-sized rounded badges with a "×N" count (`TextResponseCloud` component) — long responses truncate to a short preview and expand to their full text in a small dialog on click, and the same truncated look is mirrored in the downloadable PNG (no click interaction there, since it's a static image) — chosen specifically because it renders consistently across the manage page, Present Mode, and the downloadable PNG. New `rpc_submit_text_response` RPC + `submit-text-response` Edge Function mirror `rpc_cast_vote`/`cast-vote` closely but are kept separate rather than overloading one function with mutually-exclusive params. Voters can also go back and change an earlier answer before finishing a multi-question survey — a "← Back" button on `/vote/[code]`'s stepper, deliberately scoped to *before* finishing only (revising after completion is a separate, un-built decision). `rpc_cast_vote`/`rpc_submit_text_response` both now upsert (update the existing vote row in place if one exists for that participant+question, leaving counters untouched, instead of raising `ALREADY_ANSWERED_QUESTION`) — which also fixed the old refresh-mid-survey behavior for free, since resubmitting an already-answered question is now a genuine edit instead of a silently-discarded error. The `useBallotStore` Zustand store this replaced is gone; `/vote/[code]` now keeps its own per-question answer maps locally. A manual light/dark theme toggle (sun/moon icon in the header, `ThemeToggle` component) now sits on top of the existing `prefers-color-scheme`-based dark mode — Tailwind's `darkMode` strategy and `globals.css`'s custom properties both key off a `data-theme` attribute on `<html>`, bootstrapped before hydration from `localStorage` (falling back to the OS preference) by an inline `next/script`. Signed-in creators land on a new `/dashboard` after sign-in (previously `/lobbies`) showing stat tiles (lobbies created, voters joined, votes cast), a Draft/Open/Closed status breakdown, and a "Voters by lobby" bar chart — computed entirely client-side from data `useMyLobbies` already fetches, no new backend work. A design audit (`docs/ARCHITECTURE.md` Build Order step 37) confirmed the color/font system was already close to a tightened 60-30-10/2-font brief and fixed the real remaining gaps instead of re-branding: the home page hero is now an asymmetric two-column layout (left-aligned copy/CTAs beside a tilted demo card built from real `QRCodeSVG` + `TallyBars` pieces, not stock art) rather than everything centered in one column; every interior page's `<h1>` is a consistent 30px (`text-3xl`, up from a mix of 24–30px); a few macro spacing values drifted onto clean 8px steps (buttons, the lobbies table's cell padding, Present Mode's code badge); and the lobbies table's outer radius was deliberately squared off to `rounded-lg` as the app's one intentional contrast against its otherwise all-rounded-full/3xl/2xl visual language. A follow-up fix (Build Order step 38) addressed a real light-mode-only visibility bug: form inputs had zero background contrast against the white cards they sit in and a near-invisible `border-neutral-200`, making fields on `/create` hard to see — text inputs/textareas now get a subtly recessed `--input-bg` fill distinct from `--surface`, and every other resting card/button border darkened to `border-neutral-300`. Choice-question results can now be viewed as a bar chart (as before, with an added percentage) or a donut chart (`DonutChart`, `ChartViewToggle`, `TallyChart` in `apps/web/app/_components/`) — the choice persists across a `localStorage` key shared between Present Mode (now showing this toggle) and a new signed-in-creator-only `/lobby/[code]/stats` page (reachable from the manage page's "Detailed stats" link and the Dashboard's per-lobby chart rows), which adds voter/vote stat tiles and the same CSV/Image export the manage page already had. The manage page's own inline results are unchanged (still a plain bar chart, no toggle) — that page's access rule (any session matching `creator_id`, anonymous included) stayed as-is, while the new stats page deliberately requires a real signed-in account. `/lobbies` (both table and grid view) and Present Mode (a small link next to its status pill, shown only to the signed-in creator) also link to the stats page now, alongside the manage page and Dashboard. A UX audit pass (`docs/ARCHITECTURE.md` Build Order step 42) fixed four more things: every page now sets its own browser tab title (`useDocumentTitle`, `_components/useDocumentTitle.ts` — needed a `MutationObserver` to reliably win against Next's own title reconciliation, not just a plain `document.title` write); "Close voting" (irreversible, no way to reopen) now goes through a `ConfirmDialog` like "Delete lobby" already did, which also meant fixing `ConfirmDialog` itself — its confirm button's pending label was hardcoded to "Deleting…" regardless of the actual action; the shared `QueryClient` now sets `retry: 1` (was TanStack's default of 3) so a deterministic error like a mistyped vote code reaches its error state in ~1-2s instead of ~7-10s; and Present Mode's title/status-pill row now wraps and scales down on mobile instead of squeezing a 3-line-wrapped title against the status pill and stats link. `apps/mobile` still only has its bare framework scaffold — check the "Build Order" section of `docs/ARCHITECTURE.md` for the precise done/pending breakdown before assuming a piece exists.

## Commands

Package manager is **pnpm** (`packageManager: pnpm@9.0.0` in root `package.json`) — never run `npm install` inside an individual app, it creates a conflicting lockfile/`node_modules` outside the workspace. Install/run everything from the repo root unless iterating on one app.

```sh
pnpm install              # install all workspace deps from repo root
pnpm dev                  # turbo run dev — runs all apps' dev servers
pnpm build                # turbo run build
pnpm lint                 # turbo run lint
pnpm check-types          # turbo run check-types
pnpm format               # prettier --write across the repo
```

Per-app dev servers (each has its own scripts too):
```sh
cd apps/web && pnpm dev      # Next.js dev server on port 3000
cd apps/mobile && pnpm start # Expo dev server (then press a/i/w, or: pnpm android / pnpm ios / pnpm web)
```

`apps/mobile` has no test runner configured yet. `apps/web` has a Playwright end-to-end suite (`apps/web/e2e/`, 21 tests across every core flow — creating/voting/managing lobbies, sign-in, the Dashboard, the chart toggle + stats page, and the UX-audit fixes) — see `docs/TESTING.md` for what each spec covers and the local prerequisites:
```sh
cd apps/web && pnpm test:e2e     # headless run — requires local Supabase running + the dev server
cd apps/web && pnpm test:e2e:ui  # interactive UI mode, for debugging a single spec
```

### Supabase

Requires Docker Desktop running. From repo root:
```sh
npx supabase start        # boots the local stack (Postgres, Auth, Realtime, Storage, Studio, Edge Functions)
npx supabase db reset     # reapplies all migrations from scratch (destructive to local data)
npx supabase functions deploy   # deploy Edge Functions to the linked hosted project
npx supabase db push             # push new migrations to the linked hosted project
npx supabase config push         # sync config.toml (e.g. [auth] settings) to the linked hosted project — separate from db push
```
This repo is already linked (`supabase link`) to a hosted project. `apps/web/.env.local` and `apps/mobile/.env` (both gitignored — copy from their `.example` files) point at the **local** stack (`http://127.0.0.1:54321`) by default; swap in the hosted project's URL/anon key to test against it instead. See `packages/types/src/database.ts`'s header comment for how to regenerate types — the documented `supabase gen types typescript --local` fails on this machine (shells out to `podman` unconditionally) and needs a `docker run` workaround.

### Error monitoring (Sentry)

`@sentry/nextjs` is wired up (`apps/web/instrumentation.ts`, `instrumentation-client.ts`, `app/global-error.tsx`, `next.config.js`) and **active locally** — `NEXT_PUBLIC_SENTRY_DSN` is set in `apps/web/.env.local` (gitignored) and confirmed reaching Sentry's ingest API. **Still needed**: add the same DSN to the Vercel project's environment variables so production errors are captured too (a dashboard setting, not a code change). See `apps/web/.env.local.example` for the full variable list (the DSN plus three optional build-time-only vars for source-map upload) and `docs/ARCHITECTURE.md` Build Order step 44 for what each file does.

`docs/ARCHITECTURE.md`'s Build Order section (step 2) documents three real bugs found during verification that are worth knowing about before touching the schema: table/function GRANTs are required in addition to RLS (this Supabase version doesn't auto-expose new tables), and a PL/pgSQL variable-name collision in `generate_lobby_code()`.

### CI

`.github/workflows/ci.yml` runs on every push/PR to `main`/`develop`: a `checks` job (`pnpm lint`, `pnpm check-types`, `pnpm build`) and an `e2e` job (boots a real local Supabase stack via `supabase/setup-cli`, then runs the full `apps/web/e2e/` suite against it). See `docs/ARCHITECTURE.md` Build Order step 45.

## Architecture

**Monorepo layout** (pnpm workspaces: `apps/*`, `packages/*`, declared in `pnpm-workspace.yaml`):
- `apps/web` — Next.js (App Router). Routes live in `apps/web/app/`. Tailwind v3 configured directly (no NativeWind — see below). Uses `@repo/eslint-config` and `@repo/typescript-config` as devDependencies rather than local lint/tsconfig rules.
- `apps/mobile` — Expo + Expo Router + NativeWind. Source lives under `apps/mobile/src/`, not the repo root of the app — routes are `apps/mobile/src/app/*`, with `@/*` aliased to `apps/mobile/src/*` (see `apps/mobile/tsconfig.json`). Platform-specific file variants follow Expo's `.web.tsx` suffix convention (e.g. `animated-icon.web.tsx` next to `animated-icon.tsx`) for web vs. native implementations of the same component. `metro.config.js` has pnpm-workspace-specific symlink settings — needed for `@repo/shared`/`@repo/types` to resolve.
- `packages/eslint-config` and `packages/typescript-config` — shared lint/tsconfig presets consumed via `workspace:*` by the apps.
- `packages/types` — hand-written domain types (`src/domain.ts`, camelCase, matching what the RPCs actually return) plus generated Supabase DB types (`src/database.ts`, snake_case, matching Postgres columns — see its header for regeneration).
- `packages/shared` — the Supabase client factory + platform storage adapter interface (`src/supabase/`), a snake_case→camelCase row mapper for the one place a table is read directly instead of through an RPC (`src/supabase/mappers.ts`), and one TanStack Query hook per operation (`src/hooks/`: `useLobby`, `useCreateLobby`, `useJoinLobby`, `useCastVote`, `useSubmitTextResponse`, `useLobbyResults`, `useSetLobbyStatus`, `useLobbyRealtime`). (A Zustand ballot-selection store used to live here too — retired once per-question local state was needed for the vote page's Back button, see `docs/ARCHITECTURE.md` Build Order.) Both apps wrap their root in a `Providers` component (`apps/web/app/providers.tsx`, `apps/mobile/src/providers.tsx`) that constructs the platform-specific Supabase client and TanStack Query client.
- No `packages/ui` yet — deliberately deferred (share business logic first; apps/web has plain Tailwind, not NativeWind, until there are actual shared RN-Web components that need it).

**Turborepo pipeline** (`turbo.json`): `build` depends on upstream packages' `build` (`^build`) and caches `.next/**`; `lint`/`check-types` similarly depend on `^lint`/`^check-types`; `dev` is uncached and persistent. All four workspace packages (`@repo/types`, `@repo/shared`, `web`, `mobile`) have working `lint`/`check-types` scripts wired into this pipeline.

**Product architecture** (schema, RLS, Edge Functions, Realtime design, QR/deep-link design): fully specified in `docs/ARCHITECTURE.md` — read that before implementing any Supabase-related work, since several of the design choices there (e.g. `votes` table has zero client-facing RLS policies *and* zero table grants by design, ballot anonymity is enforced by which server function you call rather than by row-level filtering, `rpc_get_tally` is deliberately reachable only by `service_role`) are load-bearing and easy to accidentally undo with a more "obvious" RLS policy or a convenience grant.
